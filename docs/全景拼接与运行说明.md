# Seeker1 全景拼接与运行说明

本文记录 Seeker1 四目全景的厂商代码问题、拼接算法、当前性能，以及浏览器显示和关闭全景的命令。

- 适用环境：Seeker1 / RK3588S-4P 板端，ROS Noetic，四路鱼眼 1920×1200
- 当前方案：`concat_method=4` 等距柱面投影，输出 960×240
- 标定文件：`calib/kalibr_cam_chain_a4.yaml`
- 最后验证：2026-11-09

## 1. 厂商代码为什么不能开箱即用

### 1.1 仓库本身不完整

顶层仓库是相机驱动、SDK、固件和升级工具的集合，不是一套可直接运行的全景产品：

- 顶层 `launch/` 目录为空，`config/seeker_omni_depth/` 只有一个 `empty` 文件。
- README 要求执行 `roslaunch seeker 2concat_nodelet.launch`，但这些 Seeker 专用 launch/config 并不在 Git 仓库里，只在厂商烧录好的板端镜像中存在。
- 全景节点 `image_undistort` 的源码不在主仓库中，仓库只提供了预编译的 `.deb`；我们使用的源码来自单独的 `ref/image_undistort.zip`。
- README 中的 `dpkg -i ...amd64.deb` 面向 x86 Ubuntu，而板端是 aarch64；直接照做会装错架构或无法加载。

因此，在一个干净 clone 上直接按 README 操作，通常连相机 launch 和全景 launch 都找不到，更不用说重标定和调参。

### 1.2 “标定”实际是读取出厂参数

`seeker-calibrate` 调用 `script/1get_kalibr_info.py`，通过私有 USB 协议从板内读取厂商写入的相机参数，再写到 `/tmp/kalibr_cam_chain.yaml`。它不做以下任何事情：

- 不采集棋盘格/Charuco 图像
- 不做角点检测
- 不优化内参、畸变系数
- 不优化四目之间的外参
- 不计算重投影误差

所以它只是“导出出厂标定”，不是“重新标定”。当出厂参数不准确，或相机模组被更换、标定板不规整时，只能自行建立标定流程。本项目的 A4 标定流程见 `calib/标定流程.md` 和 `calib/A4重新标定命令.md`。

### 1.3 硬件和构建依赖不透明

- 相机使用 `2207:0000` 私有 USB 设备和厂商 SDK，不是标准 UVC 摄像头。
- Windows Docker 无法直接透传该 USB 设备，需要主机 ADB server 或 usbipd；README 没有覆盖这些限制。
- 板端是 aarch64 + OpenCV 4.2 的 `omnidir` 模块，Docker 镜像则是 x86；全景 nodelet 必须在板端单独编译和部署。
- 仓库没有锁定 OpenCV、ROS、编译器版本，也没有提供板端构建脚本。

### 1.4 拼接代码的质量问题

- 四路图像回调会并发写同一组 `cv::Mat`，原实现没有锁、没有重入保护。
- 处理速度低于相机 20 Hz 时没有“只保留最新帧”的机制，消息会积压，延迟越来越大。
- 每帧创建临时 Mat、`CvImage` 和输出消息，长时间运行会造成 glibc 内存碎片和 RSS 增长。
- `method=0` 中 `selected_cam` 计算后又被无条件覆盖，且投影使用的相机索引与方向索引不一致。
- 可见性阈值 `0.75`、垂直角度 `9π/24` 等参数硬编码，换一个安装角度就要改代码。
- `blend_weight` 名字像融合权重，实际代码只把它当作离轴角余弦的硬阈值；真正的羽化来自距离变换。
- 每个输出像素都要对每路相机调用一次 `cv::omnidir::projectPoints` 来建表，启动时间随输出分辨率和相机数线性增长。
- 代码中保留了调试宏、注释掉的代码和厂商字符串，缺少参数校验、运行时健康检查和自动恢复。

### 1.5 运行时缺少保障

- 没有帧率、延迟、RSS、板端可用内存的监控。
- 没有看门狗；`roslaunch` 或 `screen` 会话退出后不会自动重启。
- 板端 RTC 可能是错误时间。延迟必须用板端 ROS 时钟计算，不能用主机时间减 header 时间。
- 没有说明相机安装方向、四目顺序、盲区范围和性能预期。
## 2. 全景拼接算法

### 2.1 输入模型

每路相机使用 Kalibr `cam_chain.yaml` 格式：

- `intrinsics`：全向模型参数 `xi, fx, fy, cx, cy`
- `distortion_coeffs`：radtan 畸变参数
- `resolution`：原图分辨率
- `T_cn_cnm1`：当前相机相对上一路相机的 SE(3) 变换

`get_camera_param()` 会把 `T_cn_cnm1` 逐级相乘，得到每路相机相对 cam0 的旋转 `R` 和完整变换 `T`。因此，标定文件中的四组内参和三级基线外参必须一致；顺序错了，全景就会错位。

### 2.2 离线建表

节点启动时，`ConcatUndistorter` 为每路相机生成一张 `cv::remap` 查找表：

1. 遍历输出全景的每个像素 `(u, v)`。
2. 根据当前投影模式，把像素转换成世界坐标系中的 3D 射线方向。
3. 用 `T` 把射线变换到每路相机坐标系。
4. 丢弃相机后方的方向，并按离轴角阈值过滤边缘像素。
5. 用 `cv::omnidir::projectPoints(K, xi, D)` 把射线投影回原始鱼眼图像。
6. 如果投影点落在原图范围内，就记录源像素坐标。
7. 把浮点映射表转成 `CV_16SC2` 定点格式，运行时直接用于 `cv::remap`。

建表只做一次，但代价是 `输出像素数 × 相机数` 次投影；960×240 四目大约需要 92 万次投影，所以首次启动需要约 10 秒才出图。

### 2.3 融合权重

`computeFusionMasks()` 对每路相机的有效像素掩码做 `distanceTransform`，得到“离有效区域边界有多远”的距离图；再把四路距离图归一化成每路一张 8 位权重图。

重叠区域的融合方式是：

```text
输出 = Σ(remap(相机i) × 权重i) / Σ(权重i)
```

权重按离覆盖边界的距离羽化，而不是按入射角羽化。因此接缝处可能出现亮度跳变，尤其是两路相机曝光或白平衡不一致时。

### 2.4 单帧处理

每一帧的处理流程是：

1. 四路图像按时间同步；过期或时间差过大的帧直接丢弃。
2. 每路执行一次 `cv::remap`，把鱼眼图映射到全景画布。
3. 每路乘对应的融合权重。
4. 在 16 位累加缓冲中把四路相加。
5. 转回 8 位 BGR。
6. 发布 `/panorama/image`，同时通过 `image_transport` 发布压缩图。

### 2.5 厂商的投影模式

| 模式 | 代码入口 | 投影方式 | 适用性与问题 |
| --- | --- | --- | --- |
| `method=0` | `calcMap` | 经纬球面，按输出宽度等分条带，每路负责一条 | 简单拼接，接缝硬；`selected_cam` 逻辑有覆盖问题 |
| `method=1` | `calcMap_AVM` | 地面 BEV 平面 | 需要 `bev_ground_height`、`bev_fx`，适合俯视地面，不是 360 环视 |
| `method=2` | `calcPanoramicMap` | 球面水平带，垂直约 67.5°–112.5° | 适合四目水平环，上下覆盖少 |
| `method=3` | `calcPanoramic2Map` | 球极投影，覆盖全球 | 包含天顶/天底，四目水平安装会出现两块大黑区 |
| `method=4` | `calcEquirectMap` | 等距柱面，水平 360°，垂直 `vfov` 可配 | 当前方案，960×240，黑边仅为天顶/天底窄盲区 |

### 2.6 当前使用的等距柱面

`method=4` 的映射公式：

```text
lon = ((u + 0.5) / W - 0.5) × 2π          lon ∈ [-π, π]
lat = (0.5 - (v + 0.5) / H) × vfov        lat ∈ [-vfov/2, vfov/2]

x = R × cos(lat) × sin(lon)
y = -R × sin(lat)
z = R × cos(lat) × cos(lon)
```

其中 `R` 是 `pano_radius`，当前为 300，相当于把场景当作很远，减小近处平移视差；`vfov` 当前为 90°。上下边缘的窄黑边是四目水平环在天顶/天底方向的正常盲区，不是内存泄漏或程序错误。

### 2.7 本项目对运行管线的改造

- 每路回调只保存最新一帧，不再把历史帧排队。
- 使用 `ros::Timer` 按 `target_fps` 单线程处理；处理慢时直接跳帧。
- 用 `try_lock` 防止上一帧未处理完时重入。
- 预分配 `cam_dst_`、`cam_weighted_`、`accum16_` 和输出消息环形缓冲。
- 四路 remap 用 `cv::parallel_for_` 并行；融合使用固定大小 `CV_16UC3` 累加缓冲。
- 禁用板端会泄漏的 OpenCV UMat 路径，全部使用 CPU `cv::Mat`。
- 新增 `method=4` 等距柱面投影。
## 3. 当前性能

以下数据在 960×240、四路 1920×1200 @ 20 Hz、目标 15 FPS 下测得：

| 指标 | 实测值 |
| --- | --- |
| 全景输出 | 960×240，等距柱面 |
| 实测刷新率 | 9.5–10 FPS |
| 全景端到端延迟 | 平均约 195–200 ms，范围约 147–251 ms |
| 处理滞后 | 约 130–140 ms |
| 四路原始流延迟 | 约 20–60 ms |
| 四路时间差 | 平均约 20–25 ms |
| 节点 RSS | 约 145–190 MB 波动，无持续增长 |
| 板端可用内存 | 约 2.5–2.6 GB |
| 板端 CPU | 8 核，load average 约 2–5 |
| 首次建表启动 | 约 10 秒出首帧 |

修复前的旧二进制曾增长到约 1.8 GB，并被板端 OOM killer 杀死；修复后连续采样 RSS 在 145–190 MB 间波动，没有单调增长。延迟用板端 ROS 时钟计算，测量入口为 `http://localhost:8092/status.json`。

### 3.1 瓶颈

- 四路 1920×1200 输入，每路都要做一次全画布 remap 和融合，主要受内存带宽限制。
- 当前每路都对整个 960×240 输出画布做 remap，即使某路相机只覆盖其中一部分。
- 输出还需要 JPEG 压缩供网页显示，板端 CPU 会额外承担编码开销。
- 目标 15 FPS，实际约 10 FPS；这是算力限制，不是网络限制。

### 3.2 可优化方向

- 每路只对它实际覆盖的 ROI 做 remap，而不是全画布。
- 先把 1920×1200 缩到 960×600，再使用缩放后的 remap 表。
- 固定 10 FPS，减少无意义的重复处理。
- 分离 raw 和 compressed 发布，网页只在需要时压缩。
- 尝试 RGA/GPU 加速；当前板端 OpenCV UMat 路径有泄漏，已禁用。
- 进一步减少融合临时缓冲和拷贝。

## 4. 浏览器显示全景

### 4.1 一键启动

在 Windows PowerShell 中执行：

```powershell
cd F:\Code\Seeker1
.\docker\start-panorama.cmd
```

脚本会完成：

- 检查容器和 ADB 设备
- 推送标定文件、launch、仪表盘脚本到板端
- 启动四路全景 nodelet
- 启动网页仪表盘
- 建立 8092 端口转发

正常时会打印类似：

```text
全景已出图: 960x240, 10.0 fps, 延迟 191.0 ms, 节点 RSS 157.3 MB
打开: http://localhost:8092/
```

### 4.2 打开浏览器

启动完成后执行：

```powershell
cmd /c start "" "http://localhost:8092/"
```

也可以直接在浏览器地址栏打开：

```text
http://localhost:8092/
```

页面包含上方全景、下方四路原始鱼眼 2×2、全景延迟、处理滞后、刷新率、节点 RSS 和板端可用内存。

### 4.3 页面打不开时

确认容器和 ADB：

```powershell
docker ps
docker exec seeker1 adb devices
```

确认端口转发：

```powershell
docker exec seeker1 adb forward --remove tcp:8092
docker exec seeker1 adb forward tcp:8092 tcp:8092
```

查看板端日志：

```powershell
docker exec seeker1 adb shell 'tail -n 60 /tmp/pano_eq.log'
docker exec seeker1 adb shell 'tail -n 40 /tmp/dash.log'
```

如果重启过电脑，先执行：

```powershell
cd F:\Code\Seeker1
.\docker\start-adb-host.cmd
```

### 4.4 页面指标说明

- `全景延迟`：当前帧 header 时间到仪表盘收到该帧的板端时间差。
- `处理滞后`：全景帧时间与最新原始帧时间的差。
- `FPS`：最近 2 秒收到的最新帧数量。
- `RSS`：`pano_manager` nodelet 进程的常驻内存。
- `板端可用内存`：板端 `MemAvailable`。
## 5. 关闭全景

### 5.1 关闭命令

```powershell
docker exec seeker1 adb shell 'screen -S pano_eq -X quit; screen -S dash -X quit'
```

这条命令只关闭全景 nodelet 和网页仪表盘，不会关闭相机桥接、roscore 或容器。

### 5.2 确认已关闭

```powershell
docker exec seeker1 adb shell 'screen -ls'
```

输出中不应再有 `pano_eq` 和 `dash`。`cam` 会话是相机桥接，属于正常保留项。

### 5.3 重新启动

```powershell
cd F:\Code\Seeker1
.\docker\start-panorama.cmd
cmd /c start "" "http://localhost:8092/"
```

## 6. 常见问题

- **上下有黑边**：`method=4` 只覆盖垂直 90°，四目水平环无法看到天顶/天底，属于正常盲区。
- **画面很慢或延迟高**：确认输入是否为 1920×1200 @ 20 Hz，检查板端 load 和可用内存；当前方案约 10 FPS。
- **完全没有全景帧**：先看 `/tmp/pano_eq.log`，再确认 `calib/kalibr_cam_chain_a4.yaml` 已推送且四路话题都在发布。
- **仪表盘在但全景黑**：检查 `concat_node` 是否加载成功，以及 `method=4` 是否传入。
- **重启后页面打不开**：重新执行 `.\docker\start-adb-host.cmd` 和 `.\docker\start-panorama.cmd`。
